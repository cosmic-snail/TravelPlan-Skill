# Plan Travel Guide Skill

`plan-travel-guide` 是一个用于生成旅游攻略的 Codex Skill。它面向“目的地 + 日期 + 旅行偏好”的旅行规划场景，尤其适合需要从小红书、抖音、微博/新浪、B站和公开网页中发现 POI，再结合地图、官网或商家信息做时效性核验的攻略任务。

这个仓库把 Skill 源码、Agent 展示配置、打包脚本和校验脚本放在一起，方便版本管理、复现 `skill.zip`、安装到本机 Codex，以及后续迭代。

## 能力概览

这个 Skill 的核心目标不是生成泛泛的城市介绍，而是产出“可执行的一天或多天旅行攻略”：

- 根据旅行目的地、开始日期、结束日期和可选偏好解析约束。
- 先做平台先导主题发现，理解用户给定主题在当地通常如何被讨论、拍摄、消费和游玩。
- 从平台结果中抽取主题词、店名、商场、街区、机位、角色/IP、快闪活动、餐饮线索和路线组合。
- 建立私有的主题画像和平台证据矩阵，再由这些证据生成第二轮 POI 搜索。
- 提取并去重景点、餐厅、小吃、咖啡、商店、市集、展览、夜生活、巡礼点、机位等 POI。
- 对地址、营业状态、营业时间、预约、票务、临时活动日期等时效性信息做公开来源核验。
- 输出完整 POI 总表和按天行程，并用 TopK 形式保留不同风格的备选。

## 适用场景

适合使用 `$plan-travel-guide` 的请求：

- “帮我规划 2026-10-03 一天，围绕上海南京路，五个人，不自驾，中等预算，主题二次元。”
- “去香港旺角住一晚，想要复古文艺探店和本地特色，帮我做攻略。”
- “东京三天，情侣约会 + 动漫圣地巡礼，预算中等，节奏适中。”
- “成都两天，主题烟火气、传统文化、咖啡店。”

不适合只用这个 Skill 的请求：

- 单纯查询某家店今天是否开门。直接搜索或地图核验更快。
- 只要一段营销文案，不需要 POI 和行程。
- 完全离线、不能使用公开搜索结果的规划任务。

## 输入

必填字段：

| 字段 | 说明 | 示例 |
|---|---|---|
| 旅行目的地 | 城市、街区、酒店周边、景区或路线走廊 | 上海南京路、香港富荟旺角酒店周边 |
| 开始日期 | 行程开始日期，建议使用 ISO 日期 | 2026-10-03 |
| 结束日期 | 行程结束日期，单日行程可与开始日期相同 | 2026-10-03 |

可选字段：

| 字段 | 说明 | 默认处理 |
|---|---|---|
| 住宿位置 | 酒店、民宿、街区或地铁站 | 未提供时选择中心、交通方便区域 |
| 同行人数 | 成人/儿童/老人数量 | 默认 1-2 人 |
| 老人儿童 | 是否带老人、儿童、婴儿车等 | 默认无特殊限制 |
| 预算 | 低、中、高或更具体的人均预算 | 默认中等预算 |
| 兴趣 | 美食、咖啡、拍照、购物、博物馆等 | 默认均衡 |
| 主题 | 二次元、复古文艺探店、情侣约会、运动文化等 | 默认本地特色、烟火气、拍照出片 |
| 自驾与否 | 自驾、不开车、公共交通优先 | 默认不自驾 |
| 每日节奏 | 轻松、适中、紧凑 | 默认适中 |

## 使用

安装后，在 Codex 对话中直接点名 Skill：

```text
使用 $plan-travel-guide，帮我规划 2026-10-03 一天的旅行攻略，地点围绕上海南京路。五个人，不自驾，中等预算，节奏适中，主题二次元。
```

更完整的输入示例：

```text
使用 $plan-travel-guide，帮我规划 2026-10-03 到 2026-10-05 的旅行攻略。
目的地：香港旺角
住宿：香港富荟旺角酒店，油尖旺区旺角晏架街2号
人数：5人
交通：不自驾，步行和地铁优先
预算：中等
节奏：适中
主题：二次元、复古文艺探店
```

输出会固定包含两个一级部分：

1. `完整 POI 总表`
2. `按天行程`

## 工作流

Skill 的研究逻辑分为 6 层。

### 1. 解析旅行约束

先确认旅行目的地、开始日期、结束日期、住宿位置、人数、预算、交通方式、每日节奏和主题。只有目的地或日期缺失时才追问；其他偏好缺失时使用合理默认值。

### 2. 平台先导主题发现

不要先套固定模板，而是先搜索这个主题在目的地附近“通常怎么玩”：

- 小红书 / Rednote：发现真实游玩笔记、探店、路线、机位、避雷和排队经验。
- 抖音：发现短视频热词、拍摄角度、场景感、打卡动作和近期热门点。
- 微博/新浪：发现官方公告、应援大屏、快闪、活动日期和粉丝组织信息。
- B站：发现 vlog、吃谷路线、圣地巡礼、漫展延展路线。
- 本地媒体、文旅官网、商场官网、地图、商家页：核验地址、营业时间、活动有效期和预约要求。

如果某个平台无法打开全文，可以使用搜索结果摘要，但必须在证据中标明“搜索结果摘要”或“证据有限”。

### 3. 建立主题画像

主题画像是内部工作材料，用来决定后续搜索方向。它至少包括：

- 主题词：例如二次元可能出现“吃谷、谷子、吧唧、痛包、IP快闪、同款机位、圣地巡礼、痛楼、痛车、应援大屏”等。
- 内容类型：店铺、展览、快闪、餐厅、街区、地下商场、机位、巡礼点、路线。
- 待扩展实体：店名、商场名、作品/IP、角色名、品牌、地铁出口、街道名。
- 地理聚类：哪些 POI 常被一起出现，是否适合步行串联。
- 证据强度：高、中、低，基于重复度、具体性、新鲜度和来源多样性判断。

### 4. 维护平台证据矩阵

平台证据矩阵不作为第三个输出部分，但会影响 POI 排序和表格里的 `主题证据/来源平台` 字段。

内部矩阵格式：

| Theme | Platform/source | Query or source cue | Observed vocabulary/categories | Candidate entities | Evidence strength |
|---|---|---|---|---|---|

这个矩阵的作用是防止遗漏非典型主题解释。例如“二次元”不只等于买谷子，也可能是圣地巡礼、角色应援、同款机位、IP联动餐厅、临时快闪或城市级漫展延展路线。

### 5. 二轮 POI 搜索与核验

根据主题画像生成二轮查询，而不是按固定 POI 表机械补充。二轮查询覆盖：

- 明确 POI：店铺、商场、餐厅、展览、快闪、活动。
- 场景和行为：拍照机位、圣地巡礼、同款角度、夜景、街景、天桥、地铁站、路线。
- 别名和错写：简繁体、英文名、罗马字、旧名、粉丝昵称、楼层和铺位。
- 核验：地址、营业时间、预约、售罄、闭店、活动日期、施工、限流。

### 6. 排序和路线规划

POI 排序综合考虑：

- 平台重复度，尤其是小红书发现信号。
- 来源多样性，避免只凭单条帖子。
- 证据具体性，例如具体楼层、具体店名、具体菜品、具体机位、具体活动日期。
- 与用户主题、预算、人数、交通和节奏的匹配度。
- 地理可行性，尽量同区域聚类，减少折返。

## 输出格式

### 1）完整 POI 总表

表格字段固定如下：

| 名称 | 类型 | 风格/主题定位 | 区域 | 推荐理由 | 主题证据/来源平台 | 小红书出现频率/推荐度 | TopK/排序 | 建议停留时间 | 注意事项 | 来源帖子链接 |
|---|---|---|---|---|---|---|---|---|---|---|

要求：

- 尽量使用具体店铺、场景、楼层、机位或活动，不用宽泛街区代替 POI。
- 商场可以作为锚点，但需要列出其中值得逛的具体店铺或子点位。
- 小红书证据不足时要标注，不允许假装读过无法访问的帖子。
- 临时展览、快闪、联名、演出必须核验日期是否覆盖用户行程。
- 所有入选路线的 POI 必须出现在总表中，或者在 TopK 备选中明确标注。

### 2）按天行程

每一天固定包含：

| 时段 | 安排 | 建议停留时间 | 移动顺序/交通 | 备注 |
|---|---|---|---|---|
| 上午 |  |  |  |  |
| 午餐 |  |  |  |  |
| 下午 |  |  |  |  |
| 晚餐 |  |  |  |  |
| 晚上 |  |  |  |  |

并附 TopK 备选：

- 主题路线
- 早餐/早午餐
- 午餐
- 咖啡/甜品
- 购物/逛店
- 场景/巡礼/机位
- 晚餐/夜宵

## 仓库结构

```text
.
├── README.md
├── plan-travel-guide/
│   ├── SKILL.md
│   └── agents/
│       └── openai.yaml
├── scripts/
│   ├── package.sh
│   ├── package_skill.py
│   └── validate_skill_repo.py
└── outputs/
    └── skill.zip
```

说明：

- `plan-travel-guide/SKILL.md` 是 Skill 主体说明。
- `plan-travel-guide/agents/openai.yaml` 是 Codex 展示名称和默认提示配置。
- `scripts/package_skill.py` 生成确定性 zip 包。
- `scripts/package.sh` 打包并立刻验证。
- `scripts/validate_skill_repo.py` 校验仓库结构、Skill 关键能力和 zip 内容。
- `outputs/skill.zip` 是构建产物，默认不纳入 Git 追踪。
- `work/` 是本地历史验证目录，默认不纳入 Git 追踪。

## 安装

### 方法一：从仓库源码安装

将 `plan-travel-guide/` 目录复制到 Codex skills 目录：

```bash
mkdir -p ~/.codex/skills
cp -R plan-travel-guide ~/.codex/skills/
```

安装后，新对话中可以使用：

```text
$plan-travel-guide
```

### 方法二：从 skill.zip 安装

先打包：

```bash
./scripts/package.sh
```

生成的文件为：

```text
outputs/skill.zip
```

如果你的安装流程支持 zip 导入，导入这个文件即可。zip 内部结构固定为：

```text
plan-travel-guide/
plan-travel-guide/agents/
plan-travel-guide/agents/openai.yaml
plan-travel-guide/SKILL.md
```

## 打包

默认打包到 `outputs/skill.zip`：

```bash
./scripts/package.sh
```

指定输出路径：

```bash
./scripts/package.sh /tmp/skill.zip
```

也可以直接调用 Python 脚本：

```bash
python3 scripts/package_skill.py outputs/skill.zip
python3 scripts/validate_skill_repo.py --zip outputs/skill.zip
```

## 验证

只验证仓库源码：

```bash
python3 scripts/validate_skill_repo.py
```

验证仓库源码和 zip 包一致性：

```bash
python3 scripts/validate_skill_repo.py --zip outputs/skill.zip
```

验证项包括：

- 必需文件是否存在。
- `SKILL.md` frontmatter 是否包含 `name: plan-travel-guide`。
- Skill 描述是否以 `Use when` 开头。
- Skill 是否保留主题画像、平台证据矩阵、TopK、POI 总表和按天行程等关键能力。
- README 是否覆盖安装、使用、输入、输出、打包、验证和维护说明。
- `skill.zip` 是否只包含正式 Skill 文件。
- `skill.zip` 中的 `SKILL.md` 和 `agents/openai.yaml` 是否与仓库源码一致。

## 维护

推荐迭代流程：

1. 修改 `plan-travel-guide/SKILL.md`。
2. 用真实或模拟请求测试 Skill 行为，尤其测试之前出现过的问题。
3. 运行 `python3 scripts/validate_skill_repo.py`。
4. 运行 `./scripts/package.sh` 重新生成 `outputs/skill.zip`。
5. 复制到 `~/.codex/skills/plan-travel-guide/` 做本地试用。
6. 确认可用后提交 Git 变更。

维护原则：

- 不要因为漏掉一个 POI 就永久加一个特殊案例。
- 漏召回时应优化“平台先导主题发现、主题画像、别名扩展、二轮搜索、证据矩阵”的过程。
- 不要把小红书、抖音、B站、微博的搜索摘要包装成已阅读全文。
- 不要把临时快闪、联名活动、应援大屏当成长期 POI。
- 不要只输出商场或街区，要拆出具体店铺、楼层、机位、餐厅和备选。
- 每次改动后都要用目标主题做一次回归，例如二次元、复古文艺探店、情侣约会、本地特色。

## 常见问题

### 为什么输出必须只有两个顶层部分？

这个 Skill 的结果面向旅行使用者。固定为 `完整 POI 总表` 和 `按天行程` 可以让用户既看到候选池，也能直接照着走。平台证据矩阵和主题画像是内部工作材料，不单独作为第三个顶层部分输出。

### 为什么要先做主题画像？

同一个主题在不同城市会变成不同玩法。二次元在香港旺角可能包含圣地巡礼、天桥机位、老商场扫货；在上海南京路可能更偏百联ZX、第一百货、新世界城、迪美、华盛小亭、快闪和大屏应援。先做主题画像可以避免机械套模板。

### 小红书打不开怎么办？

可以使用公开搜索摘要、转引结果和其他平台佐证，但必须说明证据限制。时效性事实仍需通过官方、地图、商家页或本地媒体核验。

### 为什么还需要地图或官网核验？

社交平台适合发现，不适合确认事实。营业时间、闭店、预约、限流、活动日期、售罄和施工都可能变化，必须用更可靠的公开来源二次确认。

### 为什么 `outputs/skill.zip` 不进 Git？

zip 是构建产物，可以由源码复现。仓库追踪源码、脚本和说明即可，避免重复提交二进制文件。
